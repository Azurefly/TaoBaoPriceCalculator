# 架构、优化对象和最优性边界

## 1. 数据流

```
用户本人查看/授权浏览器采集
    -> 原始展示草稿（不会直接当计价基数）
    -> 商品、权益实例与结算报价核对
    -> 规则生成候选 / 人工指定候选
    -> 资源+时间+先后依赖状态搜索
    -> 已知集合内最低成本路径
    -> 每笔实际支付前复核
    -> 更新已买商品、券/红包余额，再计算剩余路径
```

UI：HTML/CSS/原生JavaScript；后端：Python/FastAPI/Pydantic；存储：仅本机原子写JSON；浏览器：可选Playwright。无云端模型调用，无返佣链接注入，无私有接口逆向。

## 2. 不可混淆的价格字段

- `display_price_cents`：页面观察到的金额，附 `display_price_kind`；可为空。
- `pricing_base_cents`：规则模拟独立确认的行总额，必须有 `pricing_base_evidence`。
- `deposit_paid_cents`：已经付过的定金；`deposit_confirmed` 表示口径核实，而非猜测。
- `cash_due_cents`：该报价从现在起仍需支付的现金，**直接使用，不再减定金**。
- `extra_cost_cents`：没有包含在结算现金报价内、但已确认还需支付的额外现金成本；计入现金总支出。
- `Resource.opportunity_cost_cents`：每单位权益消耗的经济成本；本金可以大于0，券面通常不是现金本金。

所有金额以整数分计算，Pydantic拒绝负值和浮点金额。折扣计算按配置基数算分，并用最大余数法在行之间分配；真实淘宝可能有不同舍入方式，因此模型报价始终不是平台报价。

## 3. 报价不是一个简单的价格数值

一个 `Quote` 还包括：

- 精确商品ID集合；
- `consumed` 和 `granted`：券、红包、余额等资源变化；
- `requires_done`：必须先买过的商品；
- `requires_zero`：某资源必须已经耗尽；
- 时间窗口、观察时间、来源、证据；
- 账号/地址/支付方式/商品/权益等上下文指纹；
- `ledger_complete`：完整权益消耗已核对；
- `portable_state`：能否在不完全相同的初始权益余额下复用。

默认不认定报价可移植。`portable_state=false` 时需要完整 `observed_balances`，执行时逐项相等；“两个结算页都显示了这个价格”不能证明两笔可以连续成立。

修改上下文后旧报价会被排除。程序无法检测用户在外部App中发生的所有变化，必须在每笔支付前重新读取/核对，这是已知限制。

## 4. 优化状态与目标

状态：

```
S = (已购买商品位掩码, 剩余权益资源向量, 最早可执行时间)
```

一次报价执行要求：商品不能重复买，依赖已满足，资源够用，时间窗口有效，状态条件匹配。

目标按以下顺序比较：

```
1. 最小化 Σ(现金应付 + 明确额外成本 + 消耗权益机会成本)
2. 成本相同则最小化现金应付
3. 仍相同则减少付款批次
```

已付且所有方案共同保留的必买商品定金是共同成本，不从还需付的报价中再扣。不计算未证实的退款、不把赠品标价当现金折扣、不预估未来随机收益。

每条路径必须覆盖全部必买行。可选凑单行最多买一次，按付费保留计成本。通过买一笔明确获得新券时，状态会更新，后续报价才可能可执行。

## 5. 求解方式

对有效报价图做分支限界搜索。每步至少购买一个未买过的商品，状态有限；对相同已买集合和权益余额，保留时间/成本/现金/订单数上的非劣标签。

使用保守下界：将每个可用报价的成本均分到其覆盖的必买商品，取每个商品在这些分配中的最低整数份额，再相加。这个下界忽略资源、先后和重叠约束，所以不会高估理论最低成本，但可能很松。

到达节点数或时间上限后停止，输出当前最优候选与下界。无法找到完整覆盖时不输出貌似精确的实付数字。

## 6. 三层证明不能混同

1. **输入真实性**：结算价格、SKU和权益账本是否正确？需要来源和用户/授权适配器核对。
2. **候选完整性**：是否穷举所有可能商品组合、券选择和渠道？小规模可部分穷举，大规模明确有限。
3. **求解完整性**：是否已搜索穷尽所提供的有效报价状态图？由求解器输出。

`candidate_optimal` 只解决第3层，且约束范围为本次候选图。即便“证据完整”由用户勾选，也不会神奇证明第1层来自平台；这是用户责任和采集验收边界。

## 7. 兼容活动的方式与限制

兼容来自字段模型，不来自某个节日模板。每个活动独立指定门槛基数、阶段、范围、资源、有效期、互斥和渠道。可以记录618、年货节、直播或日常店铺活动，但没有自动从活动文案完整推理所有规则。

当前不支持：复杂阶梯选赠、最低价商品免单、多币种、税费自动计算、动态价保收益、随机奖励、未明确返券、库存预测、多个地址自动切换、App自动化。已发生的最终金额可人工录入为报价；无法表达或未知的权益保持未验证。

运费、赠品保留条件、会员资格、支付渠道等不能靠一份通用折扣公式补全。

## 8. 授权适配器

只读金额和商品集合 + 有条件的购物车勾选/进入结算页面。需要部署方具有平台书面许可并提供真实DOM校准，不设伪造默认选择器。

安全允许的自动动作仅为：读取可见字段、操作原生勾选框、点击文本精确为“结算”或“结算(n)”的按钮。无任意脚本执行接口、无通用点击接口、无提交订单与支付API。

付款顺序输出是建议，不是自动支付器。自动试算也不会自动切换每张券；未知账本进入草稿。平台页面变动时应暂停并调整适配器，而非绕过风控。

## 9. 下一阶段真实环境验收的最小矩阵

应在合法授权范围内，用少量非支付试算逐项验收：

| 用例 | 必须一致的证据 |
| --- | --- |
| 同SKU不同规格/数量 | 行ID、SKU、数量及金额 |
| 单件对比合并 | 同一券实例及红包消耗不会被复制 |
| 预售+现货 | 定金扣除次数恰为1，合并门槛来源明确 |
| 同店多券 | 券详情与结算可选项一致 |
| 会员/直播/App专享 | 入口、账号资格、渠道相符 |
| 付款前后 | 已用资源消失、余量正确，旧报价失效 |
| 临近到期 | 支付完成时间仍在有效区间 |
| 退款情景 | 现金退款、权益退回及追回优惠逐项分开 |

完成这些真实场景前，不应把原型标为“开箱即用的淘宝全自动最优下单工具”。


## 0.2补充：数据版本与执行闭环

经济上下文指纹和存储版本分开：前者判断报价适用性，后者对整个项目（包括报价、候选与付款事件）做CAS。模拟写回使用计算开始时的完整版本，不覆盖期间新增报价。

已付款事件更新余额，paid_item_ids作为搜索初始已购集合。报价的完成期限取显式valid_until、缓存截止和被消耗资源截止的最小值。

顺序无关快速路径只在所有报价可跨状态复用、无返券/前置/归零条件，且全部时间窗口覆盖最坏批次完成时刻时启用；以某个未覆盖必买商品为锚，避免枚举等价付款排列。否则回退通用有序搜索。

候选生成只作提示，不给展示价补优惠。运费在最终变体比较之前计入，避免先按商品价剪掉更便宜的包邮方案。

新增search_incomplete区分“搜索预算耗尽且无完整方案”和“当前候选不可行”。
